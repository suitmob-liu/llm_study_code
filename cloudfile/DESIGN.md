## Problem Statement

在自己的 Linux 服务器上搭建一个**小型、AI-first 的文档系统**。真实动机有两个，按重要性排序：

1. **想造一个玩**，也想要一个专门为 LLM 协作设计的笔记空间——飞书/Notion 的 AI 是外挂，cloudfile 把 LLM 当一等公民
2. 作为顺带价值，**有一个脱离飞书个人/公司账号体系**的独立文档空间（虽然这个系统不会消除多账号切换本身，但能为"个人 AI-first 笔记"找到落脚点）

小团队（≤10 人）可共用，**通过邀请链接准入**（非公开注册）。定位清晰：**不是飞书的替代品，而是一个 LLM 协作工具的底座。**

> ⚠️ 诚实声明：cloudfile **不能解决"飞书账号切换烦"这件事本身**——它会变成第三个账号。如果要解决这件事，该做的是 SSO 或跨平台聚合入口，不是另建一个云文档。

## What Makes This Cool

- **LLM 原生的三件套**：读写、搜索、跟随链接。LLM 可以通过 MCP 跨整个文档库游走，不是只会"读一篇"
- **Wiki link + 反向链接**：写 `[[其他文档]]` 自动成为双向链接。你的笔记会自然形成图谱，LLM 能顺着图谱查知识
- **全文搜索（SQLite FTS）**：LLM 能"想起"30 天前写的东西，不靠 RAG 重索引
- **数据永远是你的**：`.md` 纯文本 + SQLite，想搬家随时搬
- **版本历史免费**：后台 git commit 每次编辑，回溯任何一版
- **轻而精**：≤10 人场景不需要的东西都不做——没有多租户、没有实时协同、没有复杂权限

## Constraints

- **规模硬上限**：≤10 人（设计允许扩到 30 不痛，但不为更大规模做优化）
- **部署**：用户自己的 Linux 服务器（公网 IP + 域名已备）
- **存储**：Markdown 为唯一真相源；`.md` 文件按 `用户目录/` + `shared/` 分区
- **安全**：管理员仅在服务器本地操作（SSH + CLI）；不做 Web 端管理员 UI
- **Excel/docx/ppt 支持降为 P2**（有空再做，不在 3 周计划里）
- **不做**：实时协同编辑、手机/小程序客户端、对外公开注册

## Premises

1. Builder 项目，**"好玩 + 能用"高于严格商业化**
2. **用户 ≤10 人**（设计允许扩到 30），可以用 SQLite、单进程、最朴素的认证
3. **Markdown 为唯一存储格式**；Excel/docx/ppt 属于 P2，3 周计划不做
4. **LLM 通过 MCP 读写/搜索/跟随链接是核心功能**，不是可选插件
5. **自托管**，不做公网开放注册，走**邀请链接制**（管理员 CLI 生成）
6. **Git 是后台版本历史工具**，不暴露为 git 服务
7. **数据分区**：每个用户一个目录，另加 `shared/` 共享区——权限粒度按目录

## Approaches Considered

### Approach A (Recommended): Git 仓库 + 薄壳 Web + 独立 MCP Server

**核心想法**：服务器上一个 `git init` 过的目录存所有 `.md` 文件，按用户分区。Web 后端做认证 + 编辑 + 搜索。另起一个 MCP server 进程，把 Markdown 库暴露给 LLM。

**技术栈**：

- **后端**：FastAPI (Python) 或 Express (Node)，任选顺手
- **前端**：Vite + React + Milkdown（所见即所得 Markdown 编辑器，支持 wiki link 扩展）
- **认证**：
  - **邀请链接制**：管理员 CLI 生成一次性链接（24-72h 有效，用后失效）
  - 注册后直接可用——不再有"审批"这一步
  - Session cookie，密码 bcrypt hash 存 SQLite
- **数据库**：SQLite（存用户、邀请链接、MCP token、wiki link 索引、FTS 索引）
- **全文搜索**：SQLite FTS5 虚表，文档保存时同步更新索引
- **Wiki link**：编辑器解析 `[[doc-name]]` → 后端维护双向链接索引表 `wiki_links(src_doc, dst_doc)`
- **版本历史**：每次保存后台 `git add . && git commit -m "auto: user@time"`；AI 修改加 `[ai]` 前缀
- **MCP server**：独立进程，基于 `@modelcontextprotocol/sdk`，工具集：
  - `list_docs(user_scope?)` — 列出当前 MCP token 有权限看到的文档
  - `read_doc(path)` — 读取文档原文
  - `write_doc(path, content)` — 新建/覆盖文档
  - `search_docs(query, limit?)` — FTS 全文搜索
  - `backlinks_of(path)` — 反向链接查询
  - `recent_edits(user_scope?, limit?)` — 最近修改的文档
- **部署**：systemd 三个服务（后端 / MCP / frontend 静态文件服务）+ Nginx 反代 + Let's Encrypt

**工作量**：2-3 周（全职）/ 4-6 周（业余）

**Pros**：
- 数据极简（用户分区的文件夹 + SQLite）
- 版本历史纯送
- MCP 对接天然干净——就是暴露文件系统 + 几个 SQL 查询
- 搬家只要复制目录

**Cons**：
- 无实时协同（≤10 人且主要单人写，几乎不构成问题）
- 前端要自己写（但不复杂，只有登录、文档列表、编辑器三个页面）

### Approach B: 套用 Outline/AppFlowy + MCP 适配层（不推荐）

部署现成开源协作文档，外挂 MCP server。**Pros** 多人协作、富文本、搜索现成；**Cons** 被它的数据模型绑架、造轮子乐趣去掉 80%、MCP 集成要解别人的 API。

### Approach C: Obsidian Vault + Web 网关（不推荐）

Obsidian vault 为存储，Web + MCP 读写同一文件夹。**Pros** Web + 本地双入口；**Cons** UI 自写代价大、Obsidian wiki link/dataview 语法要手动支持。

## Recommended Approach

**选 A**。理由：

1. 最匹配 "造一个玩 + AI-first" 的动机——自由度最大，外部依赖最少
2. 工作量可控：3 周可用版，≤10 人场景不需要复杂基础设施
3. MCP 对接干净——文件系统 + SQL，不是 API 包装
4. 数据主权最强：`.md` 文件 + SQLite，复制走就能搬家
5. Wiki link + FTS 让 LLM 真正有"长期记忆"——这是 12 个月愿景的地基

## Open Questions

1. **Wiki link 语法选择**：`[[doc-name]]` 友好但文档重命名会断开；`[[uuid]]` 稳定但不美观
   - **建议**：`[[doc-name]]` + 后端维护"重命名重写"——重命名时自动改所有引用（git commit 可见）
2. **邀请链接有效期**：
   - **建议**：24h 有效 + 一次性使用 + 管理员可随时吊销
3. **共享区权限**：
   - **建议**：默认全体可读可写（因为 ≤10 人且互相信任）；未来扩展为 per-file owner 即可
4. **MCP token 粒度**：
   - **建议**：每用户一 token，只能访问自己的目录 + `shared/`
5. **编辑冲突**：两人同时编辑
   - **建议**：乐观锁 + 版本号（ETag）；冲突时前端提示"本地 / 服务器 / 合并"三选
6. **AI 修改审计**：
   - **建议**：MCP 写入自动加 commit message 前缀 `[ai@username]`，可随时 `git log --grep="\[ai"` 查询
7. **LLM 修改速率限制**：
   - **建议**：MCP server 端限速（每分钟 N 次写入），防 LLM 抽风把文档改乱

## CEO 视角关键风险（从本次评审）

1. **公网暴露的风险**：LLM 能读写的文档接口暴露在公网，密码泄露/暴力破解会让攻击者通过 MCP 直接改文档库
   - **缓解**：
     - 密码强度要求（最少 12 位）+ 登录失败指数退避
     - MCP 接口也加 rate limit + token 可随时 revoke
     - 考虑 Cloudflare 前置（免费，挡大部分扫描）
2. **Wiki link 重命名**：如果不做自动重写，重命名会让所有引用变成死链，这是隐形债务
   - **缓解**：Week 2 实现 wiki link 时一并做自动重写（增加 1-2 天工作量，但省未来大量痛苦）
3. **10 人扩展到 30 人的隐形坎**：目录结构没问题，但 Session 存在单进程内存里，服务重启掉登录
   - **缓解**：Session 存 SQLite（而不是内存），成本≈0，扩展无痛
4. **Dream state gap**：3 周版本能做到"LLM 能读写+搜索+跟随链接"，但"AI 每周主动给你总结"的那一步没有在计划里
   - **缓解**：不必在 v1 做，但架构上预留——MCP 工具已经让 AI 能主动调 `recent_edits` + `search_docs`，配一个定时任务/cron 触发 LLM 调用这些工具，就能拼出周报功能

## What I noticed about how you think（更新）

- **Cherry-pick 时全选**——这说明当我把"价值/成本比"讲清楚，你能快速把不确定变成决定。这是好的产品直觉：看到架构意义就拍板，不纠结

- **对 AI-first 这件事的直觉是对的**——你选的所有 cherry-pick 都朝这个方向：wiki link、FTS、MCP 工具扩展。你心里其实一直清楚这个项目的核心是什么，只是一开始没说出来

### Wiki link 编辑交互

- **输入触发**：敲 `[[` 时立即弹出文档补全下拉（显示当前用户目录 + `shared/` 的所有文档标题）
- **选择机制**：↑↓ 键选择，Enter 确认，Esc 取消
- **链接渲染**：
  - 已存在的文档 → 蓝色 + 下划线
  - 指向不存在的文档 → 红色虚线（hover 提示"点击以创建"）
  - 被软删除的文档 → 灰色删除线（悬停显示"文档已删除，点击查看历史"）
- **点击行为**：在当前编辑区切换到目标文档（不开新窗口/新标签）——保持上下文
- **反向链接面板**：编辑区底部可折叠面板，默认展开，显示"此文档被 N 个其他文档引用"

### AI Slop 检查（自检）

按 OpenAI"设计硬规则"自查，cloudfile UI **通过**以下检查：

- ✅ 不是"通用 SaaS 卡片网格"——文档列表是文字行，不是卡片
- ✅ 没有装饰性图标圈、渐变 blob、emoji 作装饰

- ⚠️ **待实施**：CSS 变量定义颜色系统；字体避开默认栈（Inter/Arial/system），推荐 Inter + 等宽代码字体（JetBrains Mono 或 Fira Code）

## 已锁定的工程决策（来自 /plan-eng-review）

### 架构

| # | 决策 | 选定方案 |
|---|---|---|
| 1.1 | 写入原子性 | **文件系统 + git 为唯一真相源**；SQLite（FTS + wiki_links）为派生索引，drift 时通过 `rebuild-index` CLI 重建 |
| 1.2 | MCP server 数据访问 | **薄壳代理**：所有写操作 HTTP 转发到 Web 后端 API；读可直连 SQLite/文件系统 |
| 1.3 | Git commit 并发 | 单进程后端 + `threading.Lock` 包裹所有 git 操作 |
| 1.4 | Session 存储 | SQLite `sessions` 表（不用内存，重启不丢登录） |
| 1.5 | 首个管理员 | CLI `python -m cloudfile.admin init-admin`，从环境变量 `CLOUDFILE_INITIAL_ADMIN_PASSWORD` 读密码（幂等） |
| 1.6 | Wiki link 重命名 | 保存/重命名时**同步重写所有引用**，一次 git commit 包含所有改动 |
| 1.7 | 被引用的文档被删 | 软删除：`.trash/` 目录保留，FTS 清除，`wiki_links` 标 orphan，前端渲染红色"已删除" |
| 1.8 | 邀请链接安全 | 256-bit random token；DB 存 bcrypt hash；一次性使用 + 24h 过期；管理员可吊销 |

### 技术栈

- **后端**：**FastAPI (Python)** — pydantic 校验 + GitPython 成熟 + 管理员 CLI 与后端共用代码
- **前端**：Vite + React + Milkdown（wiki link 语法扩展）
- **数据层**：SQLite（WAL 模式）
- **分词**：**SQLite FTS5 + unicode61 + trigram** — 默认 tokenizer 对中文按字切会导致"机器学习"搜不到，必须启用

### 后端代码分层（单向依赖）

```
backend/
├── api/         # FastAPI routes（薄，HTTP 层）
├── domain/      # 业务逻辑（wiki link 解析、权限、保存流程、重命名）
├── storage/     # 数据层（SQLite models、git 操作、文件系统）
└── admin/       # CLI 命令
```

依赖方向：`api/` → `domain/` → `storage/`。MCP server 通过 HTTP 调用 `api/`，不直接 import 业务代码。

## 失败模式与监控

### 必须的日志（3 种独立文件 / 轮转）

1. **认证审计** `log/audit.log`：登录成功/失败、邀请链接使用、管理员操作
